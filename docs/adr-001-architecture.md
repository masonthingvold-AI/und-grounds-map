# ADR 001: Architecture for the UND Grounds operations platform

Status: accepted, September 7, 2026
Decided by: Mason, with Claude and ChatGPT/Codex each having reviewed the other's blueprint. Codex's three qualifications (native shell, tamper evidence versus immutability, one repo with separate working copies) are folded into decisions 3, 4, and 8.
Supersedes: the stack and roadmap sections of `docs/technical-blueprint-v0.1.md` (Claude) and `docs/technical-blueprint-codex-v0.2.md` (Codex), which stay in the repo as references. Where those documents disagree with this one, this one wins.

## Decision

1. **Backend: Supabase** (Postgres with PostGIS, Auth, Storage, Realtime, Edge Functions). No custom NestJS backend, no React. Schema lives in `supabase/migrations/`, versioned with the code.
2. **Critical writes go through database functions or Edge Functions, not direct table inserts.** Dispatch, assignment, reassignment, asset reservation, inventory movement, certification checks, mode pivot, and service record finalization are each one transactional `security definer` function that validates and computes server side. Row Level Security is defense in depth, not the enforcement layer. Workers never supply computed fields (geofence result, hashes, sequence numbers).
3. **One repository, separate working copies.** Each assistant works in its own checkout and pulls before starting. The existing map is preserved as is; shared code, the worker shell, database migrations, and documentation are organized alongside it in this repository. The map stays the first screen and the seed data source. `index.html` keeps its no-framework rule and stays usable as a double-click viewer for the map layers only. The authenticated operational app runs over HTTPS (GitHub Pages or Supabase hosting) with a service worker; nothing promises the full app works from a `file://` URL. The split of `index.html` into modules is agreed in AGENTS.md before anyone edits the shell.
4. **Worker app: web first, Capacitor as the native shell, background tracking unproven until tested.** Phase 1 tracks location only while the app is open and on shift, with a visible tracking state and a staleness marker. Capacitor is the chosen native shell for the worker app, but the shell alone does not give background tracking: that needs a suitable background geolocation plugin or a native implementation, the right permissions, and locked-screen testing on the crew's actual iPhones and Android phones through battery saver, denied permission, lost network, and shift end. Plugin cost and reliability are unverified and are part of the gate. Until that gate passes, no document or conversation with Chad promises screen-locked tracking. Either way the codebase stays one.
5. **Zones are versioned, never overwritten.** `zones` holds identity; `zone_versions` holds immutable geometry. Every service record, task, and route leg references a `zone_version_id`. Imports and hand tracing create new versions.
6. **Service status is scoped.** Status rows are keyed by zone version, event (storm or season), and activity. Cleared, salted, and sanded are separate facts with their own timestamps and actors, not one enum.
7. **Location assessment is computed server side with accuracy and age.** Result is one of `inside`, `boundary`, `ambiguous`, `outside`, `unavailable`, using geography distance in meters, the reported accuracy radius, sample age, and the zone class. A wide accuracy radius on a narrow walkway is `ambiguous`, never `inside`. No fixed buffer.
8. **Evidence integrity: tamper evidence, not immutability.** Append-only `evidence_events` with a per-record sequence and hash chain (not one global head), canonical JSON serialization, hashes computed by the database function, and a nightly signed anchor digest stored outside Supabase (emailed and written to a second provider). This proves whether a record changed after the anchor; it does not stop a privileged account from changing or deleting a photo in Supabase Storage, which does not support object lock. Access policies that deny update and delete to app roles are access control, not a retention lock. If a retention lock is required, originals are copied to a bucket on a provider that supports it. That distinction stays explicit in every document and demo until records staff approve the archive and retention approach. Originals are never replaced by stamped derivatives.
9. **Retention is a records decision, not a code default.** No retention period or deletion schedule is set for service records, photos, raw GPS, or derived presence until UND records staff and counsel state one. The ten year figure in the v0.1 blueprint is withdrawn. Legal hold is a flag on `evidence_objects` from day one so it exists when they ask for it.
10. **Mode pivot has a revision.** `operating_state` carries a monotonically increasing revision; a pivot takes `expected_revision` and an idempotency key, commits the state change and an outbox event in one transaction, and clients acknowledge the revision. Active work stays visible across modes.
11. **Weather automation starts as recommendations.** Manual dispatch first. The rule engine evaluates stored input snapshots and proposes call-outs; a supervisor approves each one. Promotion of any rule to automatic call-out requires written acceptance criteria (agreement rate between recommendation and supervisor decision over a full season, zero duplicate call-outs, defined behavior on stale or missing data) and operational approval from Chad, recorded in `docs/`. Rules define freshness, forecast versus observed, storm window, cooldown, reset, and missing-source behavior. Storm total accumulation comes from a defined window, not summed cumulative readings.
12. **Timecards are confirmed, not inferred.** Zone presence from GPS suggests time entries; the worker or lead confirms them. Breaks, travel, overlapping zones, and daylight saving transitions are handled explicitly. Hours worked in other departments are marked as unknown until HR provides a feed.
13. **No policy thresholds are seeded as live.** Student hour caps, consecutive hour limits, rest rules, and safety training expiries ship as disabled examples with a `source` field. They turn on when HR or the safety office supplies the effective-dated policy.
14. **Concurrency.** Exclusion constraints on asset reservations and on active shifts per person. Idempotency keys on every command. Partitioned tables include the partition column in their primary key, or are not partitioned in the pilot.
15. **Reports are in the MVP.** A minimal evidence export (one zone, one date range, every record with photos, assessment, materials, corrections, and chain verification) ships with phase 1. Rich analytics come later.
16. **My UND integration and any public status page are out of scope** until the internal MVP has run a season. Kept as a proposal in `docs/app-spec-v0.2.md`, not a commitment.
17. **Institutional blockers block production, not building.** Identity (UND SSO), hosting on a UND domain, HR feeds, records retention, and GIS rights are required before live use with real employees. Prototyping with synthetic people and real geometry proceeds now.

## Planning assumptions to confirm with Mason

- Crew size 10 to 20 in season; 3 to 5 completions per worker per day; two photos per completion at about 300 KB. That is roughly 60 MB of photos a day and about 17 working days per gigabyte, so the Supabase free tier is a prototype allowance, not a season. Budget for the paid tier before the pilot goes live and measure real volume in week one.
- Ten hour shifts, 15 to 30 second sampling while moving, slower when stationary. Tune on real phones.

## Division of work between the assistants

- **Claude owns:** the database (migrations, PostGIS, database functions, RLS policies, triggers, seed from `data/*.geojson`), the map and its editing tools, the Edge Functions for weather and reports, and migration verification.
- **Codex owns:** the worker interface (My Day, shift start and stop, proof of service form, offline queue and replay, acknowledgments) and the supervisor dispatch screens, built against the function signatures and views Claude publishes in `docs/api-contract.md`.
- Neither edits the other's area without a note in the commit and a pull first. Neither invents a second schema. Both keep decisions in `docs/`, not in chat.

## Build sequence and gates

1. Push the repo. Both assistants clone. Claude publishes `docs/api-contract.md` (function names, arguments, return shapes, views) before Codex writes a screen.
2. Migrations 0001 to 0010: people, crews, capabilities, certifications, zones and versions, assets, shifts, location samples, tasks and assignments, service records and evidence events, operating state and outbox. Gate: migrations apply clean on an empty project, policies tested with the real runtime role, seed loads every GeoJSON feature as a zone version.
3. Vertical slice on two real phones: login, one task, qualified assignment, acknowledgment, foreground GPS with staleness, before and after photos, quantity, offline replay, supervisor review, evidence export. Gate: retries produce one record; a worker cannot read another crew's protected rows; a tampered row fails chain verification.
4. Background tracking gate: Capacitor build on the crew's phones through screen lock, battery saver, denied permission, lost network, shift end. Pass or fall back to a native module.
5. Revisioned pivot: one connected and one disconnected device; concurrent pivots resolve deterministically; summer work survives.
6. Then fleet, materials ledger, time confirmation, policy alerts, cross-crew redistribution, and only after that weather recommendations and route guidance.

## Consequences

- Cheaper and faster than the Codex v0.2 stack, and it can start before UIT is involved. The cost is that Supabase is a vendor: the schema is plain Postgres so it can move, but Auth, Storage, and Realtime would need replacing if UND requires on-premises hosting.
- Web-first means the first pilot cannot promise screen-locked tracking. That is stated plainly to Chad rather than discovered in a storm.
- Database functions instead of direct inserts mean more SQL up front and less client code. That is the right trade for a liability record.
